# Сквозной запуск аналитики

Этап 17 объединяет подготовку JSONL, загрузку и сверку БД, разметку, пакет DataLens и управленческий PDF.
Повторное обучение ML и создание графиков в аккаунте DataLens выполняются отдельно: здесь можно подключить
проверенные результаты уже выполненной кластеризации.

## Перед первым запуском

Установите зависимости проекта и `reporting` extra, задайте `POSTGRES_*` в `.env`, примените миграции
до `e1f2a3b4c5d6`. Миграции, создание облачных ресурсов и выдача прав не выполняются оркестратором автоматически.
Для этого процесса нужен пользователь, способный загружать данные в analytics; BI-роль только с SELECT не подходит.

Возьмите `configs/analytics-pipeline.example.json`, сохраните рабочую копию и задайте:

- `source`: локальный исходный Yandex JSONL;
- `run_name`: уникальное имя папки процесса, например `dentistry-001`;
- `runs_root`: где сохранять результаты (по умолчанию `data/analytics-runs`);
- `taxonomy` и `rules`: согласованные версии конфигураций;
- `create_pdf` и `font`: нужен ли PDF и путь к TTF с кириллицей;
- оба `ml_*_manifest`: манифесты существующего корпуса и reassignment либо оба null для rules-only.

Запускайте команды из корня проекта. Пароль БД в JSON не указывается и в журнал не записывается.
Предварительная проверка только читает файлы и БД:

```bash
.venv/bin/python scripts/run_analytics_pipeline.py configs/analytics-pipeline.example.json --dry-run
```

Полный запуск:

```bash
.venv/bin/python scripts/run_analytics_pipeline.py configs/analytics-pipeline.example.json
```

Остановка после выбранной стадии и продолжение:

```bash
.venv/bin/python scripts/run_analytics_pipeline.py configs/analytics-pipeline.example.json --stop-after assess
.venv/bin/python scripts/run_analytics_pipeline.py configs/analytics-pipeline.example.json --resume
```

`--dry-run` проверяет наличие файлов, их контрольные суммы, PDF-зависимость и наличие витрин; полная проверка
контракта каждого отзыва выполняется стадией prepare. Просмотр выдаёт режим rules_only/hybrid.

## Результаты

```text
data/analytics-runs/dentistry-001/
  pipeline-state.json         состояние, ID в БД и контрольные суммы
  01-prepare/                 приватный canonical JSONL и manifest
  02-load_feedback/           контрольная точка загрузки (данные в БД)
  03-reconcile/               агрегатная сверка БД
  04-adapt_ml/                темы отзывов, если заданы ML-манифесты
  05-assess/                  оценки категорий и manifest
  06-load_problems/           контрольная точка загрузки оценок (данные в БД)
  07-datalens/package/        четыре SQL-источника и спецификация дашборда
  08-pdf/report/              PDF, агрегатный JSON и manifest, если create_pdf=true
  attempts/                  сохранённые незавершённые попытки
```

Не путайте три идентификатора: `run_name` — папка процесса, `dataset_id` — snapshot отзывов в БД,
`problem_run_id` — запуск разметки в БД. Именно последний подставляется в SQL DataLens и PDF.
Тексты в 01-prepare приватные; папка запуска создаётся с правами 0700. Не коммитьте её.

## Продолжение и ограничения

Завершённые локальные файлы проверяются по SHA-256. Код workflow, входной датасет, конфигурации, шрифт
и спецификация DataLens привязаны к запуску; изменение требует нового run_name. Повреждённые завершённые
файлы блокируют resume. База данных повторно проверяется через идемпотентные загрузчики и сверку исходных
отзывов. Если ID snapshot изменился или содержание сохранённых оценок изменилось, продолжение блокируется:
создайте новый запуск, чтобы выпустить обновлённый отчёт после ручной проверки разметки.

Незавершённые локальные результаты при resume переносятся в attempts, после чего стадия выполняется заново.
Они не удаляются. Если процесс упал после COMMIT, повторный загрузчик найдёт существующий артефакт по checksum.
Запуск без --resume в существующую папку запрещён. Завершённый запуск можно продолжить для повторной проверки
контрольных точек: PDF и пакет при этом не перезаписываются.

Файл `.pipeline.lock` блокирует параллельное выполнение. После аварийного завершения всего процесса он может
остаться: сначала убедитесь, что процесс действительно завершён, затем удалите только этот lock и используйте
--resume. При обычной ошибке блокировка снимается автоматически, состояние становится failed.

Процесс не является одной общей транзакцией: каждая загрузка БД атомарна, а уже завершённые шаги сохраняются.
Поэтому failed не означает откат всего процесса. Журнал не хранит тексты исключений, которые могут содержать
отзывы или параметры БД. Для диагностики смотрите current_stage и проверяйте входные контракты соответствующей
отдельной командой. При изменении конфигураций, разметки или выбранной базы используйте новый запуск.

Статус completed означает завершение локальной аналитической цепочки; он не означает, что дашборд создан
в аккаунте DataLens или демонстрационная среда развёрнута.
