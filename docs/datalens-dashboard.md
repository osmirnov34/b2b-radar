# DataLens: первый дашборд

Подготовка этапа 15 создаёт SQL-источники, формулы и спецификацию 12 графиков. Дашборд уже создан пользователем
в DataLens; подключения, датасеты и графики нужно собрать в его воркбуке. `dashboard.json` — наша спецификация
сборки, **не файл импорта DataLens**. Скрипт не входит в аккаунт и не публикует данные.

## Подготовка проекта

Примените миграции до `e1f2a3b4c5d6`, загрузите и сверьте реальные отзывы и результаты разметки. Выберите один
числовой ID из `analytics.problem_runs`. Сгенерируйте пакет, например для запуска 1:

```bash
.venv/bin/python scripts/prepare_datalens_dashboard.py 1 data/reports/datalens-run-1
```

Пакет можно создать без работающей БД: существование выбранного запуска этим действием не проверяется.
В нём четыре SQL-файла, `dashboard.json`, README и manifest с SHA-256. Повторная запись в ту же папку запрещена.
Данные и пароль подключения в пакет не включаются. Каждый SQL фиксирует один run_id; не удаляйте это условие.

Новая схема `analytics_bi` содержит четыре источника:

| Источник | Одна строка | Использование |
|---|---|---|
| organization_overview | Запуск × клиника | Общие KPI, сравнение клиник, распределение рейтингов |
| organization_monthly | Запуск × клиника × месяц | Динамика объёма и рейтингов |
| category_overview | Запуск × клиника × категория | Жалобы, сильные стороны, качество разметки |
| category_monthly | Запуск × клиника × категория × месяц | Динамика жалоб |

В категориях присутствуют клиники без сигналов — с нулевыми счётчиками и реальным числом отзывов в знаменателе.
В месяцах без исходных отзывов строк нет: пропуски не означают нулевую долю жалоб. Метаданные категорий берутся
из snapshot соответствующего запуска. Rejected исключены из сигналов, но сохранены в счётчике качества.

## Подключение с ограниченными правами

DataLens нужен доступ к PostgreSQL по сети; `localhost` ноутбука не подходит облачному сервису.
Выбор и создание облачной БД относятся к развёртыванию и отдельно согласуются с владельцем.

Администратор один раз выполняет `scripts/datalens_reader_role.sql` в выбранной БД после миграций. Файл создаёт
новую NOLOGIN-роль `b2b_radar_bi_reader` и даёт SELECT только на четыре BI-представления. Затем создаётся
отдельный LOGIN с членством в этой роли и паролем, заданным через `psql \password`. Группа не получает доступ
к приватным таблицам. Не используйте для DataLens владельца базы, superuser или учётную запись приложения.
Если роль уже существует, скрипт намеренно завершается ошибкой: проверьте её права, не выдавайте широкие GRANT.

В воркбуке выберите «Создать подключение» → PostgreSQL. Укажите хост, порт, БД и новый LOGIN, настройте TLS
и сетевой доступ согласно официальной инструкции. Для использования подготовленных запросов нужен SQL на чтение.
API-токены этапа 14 здесь не используются: DataLens читает PostgreSQL непосредственно.

## Четыре датасета и вычисляемые поля

Создайте по датасету на каждый SQL-файл из пакета, вставляя текст в источник SQL/подзапрос. Не объединяйте
датасеты JOIN-ами в интерфейсе: повторяющиеся строки категорий размножат числа отзывов. В каждом источнике
оставьте `run_id`, `organization_id`, `organization_name`, `sample_sufficient` измерениями, без агрегации.
`month` задайте типом «Дата»; `category_id` и `category_name_ru` — измерения категорий.

Создайте только подходящие источнику вычисляемые поля из `metrics` в `dashboard.json`:

| Поле | Формула | Источники |
|---|---|---|
| reviews | `SUM([feedback_count])` | organization_* |
| average_rating | `SUM([rating_sum]) / SUM([feedback_count])` | organization_* |
| low_rating_share | `SUM([low_rating_count]) / SUM([feedback_count])` | organization_* |
| complaint_share | `SUM([complaint_count]) / SUM([feedback_count])` | category_* |
| mixed_share | `SUM([mixed_count]) / SUM([feedback_count])` | category_* |
| praise_share | `SUM([praise_count]) / SUM([feedback_count])` | category_* |
| accepted_complaint_share | `SUM([accepted_complaint_count]) / SUM([feedback_count])` | category_* |
| unreviewed_complaint_share | `SUM([unreviewed_complaint_count]) / SUM([feedback_count])` | category_* |
| rejected_assessments | `SUM([rejected_count])` | category_overview |

Доли форматируйте как проценты (значение 0.2 → 20%), рейтинг — с двумя знаками. Нельзя использовать
`AVG(average_rating)` для объединения клиник и среднее их долей: нужны взвешенные формулы из таблицы.
Доля по категориям имеет смысл только при наличии category_id в группировке; не суммируйте категории в общий
«процент проблем». Отдельного подсчёта уникальных людей нет — считаются отзывы. Не показывайте общий объём
отзывов из category_*: знаменатель в них повторяется для каждой категории.

## Размещение графиков

В уже созданном дашборде разместите:

1. Верхний ряд: количество отзывов, средний рейтинг, доля оценок 1–3.
2. Таблица клиник: ID, название, отзывы, средний рейтинг, доля низких оценок. Группируйте по ID и названию:
   совпадающие названия разных организаций не должны объединяться.
3. Горизонтальные диаграммы: жалобы, сильные стороны и mixed по категориям; сортировка по доле убыванию.
   category_id используйте как ключ/детализацию, category_name_ru — как подпись.
4. Отдельная диаграмма принятых и предварительных жалоб по категориям; накопление допустимо только для этих
   двух взаимно исключающих счётчиков. Счётчик отклонённых оценок поставьте в блок качества разметки.
5. Линии по month: средний рейтинг и число отзывов. В отдельном графике — доля жалоб, цвет/серия category_id.

Точная привязка каждого графика к источнику, измерениям и метрикам находится в `charts` спецификации.
Для графика динамики категорий никогда не удаляйте категорию из серий или детализации.

Селектор клиник связывается со всеми четырьмя датасетами через алиас organization_id; названия используйте
только для отображения. Селектор категорий влияет на category_*, не на общий рейтинг и объём. Селектор month
влияет только на месячные графики; обзорные KPI показывают весь период запуска — подпишите это рядом с ними.
`sample_sufficient` оставьте необязательным фильтром: по умолчанию показываются и малые выборки. Для месячных
графиков порог 30 применяется к месяцу, для обзорных — ко всему периоду; это следует явно подписать.

Добавьте текст: «Отзывы описывают восприятие пациентов. Предварительные оценки требуют проверки.
Выборка может быть смещена; показатели не измеряют финансовые потери и не подтверждают медицинскую ошибку».
Это исследовательский дашборд для руководителя и аналитика. Публичное распространение проверяется отдельно.

## Проверка собранного дашборда

Сверьте число отзывов с выбранным snapshot, сравните две клиники с разным числом отзывов и проверьте
взвешенный рейтинг. Выберите клинику без сигналов в категории: должен быть ноль, а не исчезновение клиники.
Проверьте фильтр категорий, пустой месяц, различие accepted/unreviewed и отсутствие текстов/авторов.
Завершение этапа в DataLens фиксируется после ручной сборки и такой проверки, а не после генерации пакета.
